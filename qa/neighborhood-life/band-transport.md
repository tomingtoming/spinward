# 専用道路とJCTの土地計画

tomingが全域計画に高速道路相当の道路を別途用意する提案を了承し、実装中に
「ジャンクションもある？」と質問。今回の具体案は東縁本線、南端の物流支線と
そのJCT。道路・川・拠点の配置はSpinward向けのAI設計案で、作品の地図復元でも
原画から高速道路の形式を同定したものでもない。元画像の追加走査や変更はしていない。

## 実装と適用範囲

`bandExpresswayLand.ts` の路線・IC・JCT・一般道の立体横断候補を、
`reserveBandExpressway` が専用の有向グラフと用地へ変換する。
`planBandTransport` はその用地とICの一般道接続点を `planBandStreets` に渡す。
一般道・アクセス需要は、専用道路用地を避けた土地から再生成される。

- 東縁本線39.200km、南端物流支線1.708km。端部・施設帯に寄せた独自案。
- IC7か所。中間の4か所は4本の出入ランプ、端部の3か所は1本ずつの入口・出口。
  端部で道路を接続のない棒として残さず、一般道へ終端する。
- 南部物流JCT1か所。支線との4方向の分岐・合流と、本線の双方向通過。
  一般道へ降りる機能をJCTに追加せず、近隣のICが別に担う。
- 本線の用地幅120m、支線100m、ICとJCTはランプ全体の包絡を予約。
  これは建物を置かない計画用地であり、車道幅や工学規格を意味しない。
- 支線の渡河予約は1か所。川・護岸予約領域の中心線横断310mであり、
  310mの橋桁を設計済みという意味ではない。本線は川を渡らない。
- 一般道が専用道路をくぐる候補5か所。本線4、物流支線1。
  支線横断を加え、南端ICから整備地区への一般道を1.87kmに収めた。
- IC接続先は用途需要とは別に指定し、IC付近へ住宅需要を自動追加しない。
  旧市街は川の渡河制約を考慮して到着地区ICへ接続。個別候補経路は旧候補の
  10.81kmから5.30km、最終的に共用する一般道上の最短距離は5.32km。
  地区ごとの最適なIC間隔・密度や既存Placesの保護は引き続き検討する。

元の15地区中心は移動・削除しない。生成した一般道は633区間、接続成分1、
中心と需要の孤立0、配置不足0、ICから地区への接続12組。
区間数は交差で分割後の数で、交通量や描画負荷の評価ではない。

ICから既存の幹線へ到達したら、その先を共用する。同じICの接続先地区を増やすだけで
平行する幹線を増設しない。集散道路の接続候補にも、直線で到達可能な最寄りの道を
加えた。距離だけで近い8候補に絞ると、専用道路の反対側の候補だけが残り、すでに
同じ側にある道路を無視して遠くの立体横断へ似た枝を重ねる問題があった。
この修正は一般道だけの生成にも適用。比較図の「専用道路なし」は修正後の生成器を
同じ土地入力で動かした578区間の対照であり、過去の575区間の保存画像ではない。

**現在の3D実行経路へはimportしていない**。今回の結果を現地の高速道路の完成と
扱わない。道路幅・曲率・合流長・縦断勾配・桁下高・上下線離隔・支持柱の成立、
一般道の短区間・鋭角の整理、敷地・建物、交通・案内、昼夜の遠景・LOD、他の2帯は未完。
`level` と `structure` は接続階層と立体設計の意図で、実際の高さではない。

## 接続の検査

専用道路はノードIDで明示した接続のみを使用する。一般道の `bandGraph` へ混ぜず、
平面上の交差や、逆向きの車道が近いことを接続とみなさない。
転送点はICの一般道ゲートだけ。経路は途中のICゲートを折返しの近道に使わない。
立体横断は `underpass` として記録し、元の水上橋とは区別する。

新規9テストで次を検査する。

- 全7IC間の42方向で、切れ目のない有向経路が得られる。途中のICで一般道へ降りない。
- 全ノードに入口・出口があり、描いた道路端と接続IDの位置が一致する。
- JCT閉鎖は支線の双方向接続を失わせ、本線の双方向通過と一般道を維持する。
- 特定ICの閉鎖はその出入りだけを止め、本線を切らない。
- 平面上で一般道と専用道路が交差する非転送点には、一般道の立体横断指定がある。
- 用地内に需要地点・地区中心を配置しない。一般道は許可した横断のみで用地を通る。
- 同じICの接続先に既につながっている地区を足しても、一般道の幾何は変わらない。
- 用地の帯外流出、地区中心の侵食、保護地への侵入、未指定の渡河、ICの接近を拒否。
- 決定性と入力不変、立体横断候補を除いたときに勝手な横断を作らないこと。

## 比較図と再現

```sh
OUTPUT_DIR=/absolute/path/to/evidence bun qa/neighborhood-life/band-transport.ts
```

生成される `map.html` は外部依存のないHTML。専用道路なしの一般道と、用地・IC接続を
加えた案を同じ範囲で比較し、出発／到着IC、JCT閉鎖、集散道路と用地の表示、JCT・
IC・渡河・北端の拡大を操作できる。橙色は専用道路だけの経路。
JCT閉鎖時の専用道路到達不可を、物流地区そのものの孤立と表示しない。

根拠・画像・生成JSON・検査ログは `qa/webxr/evidence/band-transport-20260914/`。
詳細比較のviewBoxは一致、左右570×550 CSS px、閲覧1280×720。
通常ブラウザで開通／閉鎖、閉鎖中の本線通過、IC拡大、経路反転を確認。
独立画像レビューで、重なる対向ランプが読めない、閉鎖状態が単独画像で不明、
一般道と平面交差に見える、という指摘を受けた。4方向を個別に強調するボタン、
詳細内の方向名と閉鎖札、立体横断・渡河予約・南北方向の注記を追加し再レビュー。
接続意図の説明は改善を確認。ただし4本の物理的な離隔はこの縮尺・段階では未検証。
DOMでは4ボタンで4種類のpath、閉鎖時の強調0・4ボタン無効化、集散道路と用地の
表示切替を確認。

最終コードの `bun test` は1000件中999成功・既存1件時間切れ、171.38秒。
64,000棟の既存検査が10秒の上限を22ms超過した。値の不一致ではない。
コードも検査基準も変えず該当検査を単独で実行すると9.12秒で成功した。
初稿時の全体999件はすべて成功していたが、最終コードの全1000件が一括で成功した
とは報告しない。今回の新規9件は最終全体実行で成功。TypeScript・production buildも
最終コードで成功し、既存の大きいchunk警告だけが残る。

## 費用と残る形状上の制限

`bun qa/neighborhood-life/band-plan-audit.ts --transport` で、専用道路予約・一般道・
平面上の交差監査を含む計画生成を1回準備後5回計測。中央値3069.1ms、
2913.1〜3263.9ms。描画や建物生成、実機Questを含まないApple M1 Pro上のCPU計測。

一般道の総延長195.21km、閉路48、行き止まり164、最短区間0.639m。
25度未満の分岐は初稿14か所から6か所へ減ったが、**最小0.466度の合流が残る**。
これを走行可能な交差点や敷地として扱わない。専用道路の上下線とランプの立体化に
加え、一般道の近接合流の統合と曲率・幅を解くことが、敷地生成と3D適用の前提。
現在の実行アプリにこの生成費用は加算していない。

3D・VR UIには変更がないため、今回の計画の合否をWebXRの合否で代用しない。
playwright-webxr 0.3.0を維持し、道路・交通・案内を3Dへ適用する時に実際の入場・
操作・左右眼・退出／再入場を改めて検査する。実機Questでの評価は未実施。
