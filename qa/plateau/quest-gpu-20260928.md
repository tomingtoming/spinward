# Quest GPU/depth diagnosis

The user still reports poor performance on physical Quest after the CPU and
draw-call optimizations. This investigation does **not** establish a physical
Quest performance improvement. Keep the 100% framebuffer scale and current
default logarithmic depth until the user compares the diagnostic URL.

The [Three.js renderer documentation](https://threejs.org/docs/pages/WebGLRenderer.html)
states that logarithmic depth uses `gl_FragDepth`, disabling the Early Fragment
Test optimization and potentially reducing performance. This makes depth a
credible hypothesis, but the desktop result does not identify the Quest driver
bottleneck by itself.

Other tested appearance-preserving candidates did not show a meaningful gain:

- Hide zero-intensity lights: 29.56 / 46.60 ms GPU median (Shibuya / Omiya).
- Remove covered overview indices on CPU: 29.37 / 46.36 ms, saving only about
  9–12k triangles. Index changes were performed once at mode entry, not per frame.

Neither experiment was shipped. An earlier profiling harness recopied indices
per frame; it was interrupted and its partial results were discarded.

capped time. Real 10 Hz frames therefore appeared as 20 FPS. `rawDeltaSeconds`
now supplies performance reporting while simulation retains the existing cap.
The adaptive XR governor already used raw frame timestamps and was unaffected.

Unit tests: 10 passed / 53 assertions across game loop, FPS meter and governor.
TypeScript and fixed Vite metro build passed. The XR cadence test injects frame
timestamps to check the meter; its 10/72 Hz values are **synthetic**, not observed
performance. The first test harness incorrectly advanced time per subscriber
instead of per XR frame and failed (6 instead of 10); the corrected harness
shares the timestamp across all subscribers of the same frame.

## Physical check / next decision

[Quest comparison: plain depth](https://spinward-metro-candidate.toming.workers.dev/?city=tokyo&preset=izma&depth=plain)
changes only the depth mode via the existing URL option; it keeps 100% resolution.
Remote surfaces may flicker because ordinary depth loses precision over the
colony's large scale. This is a diagnostic, not the final visual-quality choice.
Remove `depth=plain` or use `depth=log` to return to the default mode.

Physical Quest feedback (user, 2026-09-28): distant z-fighting became severe and
the user requested stopping the plain-depth experiment. Plain depth is rejected
as the rendering default. The user did not report a performance comparison, so
the physical performance hypothesis remains unconfirmed. Return using
`?city=tokyo&preset=izma&depth=log`; this explicitly overrides any stored choice.
Opening the comparison URL itself does not persist its depth choice. Only the
in-app depth toggle writes the stored preference. The deployed default remains
logarithmic depth; no deployment rollback is required.

Any subsequent optimization must retain stable distant surfaces. A near/far
precision split would need independent XR projection,
transparency, stereo and GPU-cost validation; simply enabling plain depth as
the default is not the accepted fix.
